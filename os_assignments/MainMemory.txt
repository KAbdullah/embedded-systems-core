Background
----------

The CPU only has access to registers and Memory, specifically Main Memory, this is because all other memory is inherently
very slow and would cause the CPU to stall way too much for anything productive to happen 

What the address sees is two things:

1. It sees address + a read request from the controller 
2. It sees and address + a write request + data that can be stored 

The CPU can access a register in one CPU cycle while main memory though faster than secondary memory, 
still takes multiple CPU cycles. 

However, in order to circumvent the main memory's speed, cache is placed in between the registers and the main memory
to help speed up running the processes

Protection
----------

We need to protect memory access to ensure that proper legal operations take place.
This means placing base and limit registers in order to ensure unauthorized access doesn't take place.

In Linux and Windows the lower memory is User Space where things like variables, pointers, heaps and stack live.
While in higher mmeory Kernal space usually lives. This is what usually happens.

The Base register usually holds the legal minimum memory allowed while 
the Limit register stores a range value (which is usually the range of the process, aka. how big it is)

These two values, the base + the limit usually define the legal logical (virtual) memory a process has.

The MMU usually does a quick check to see if the logical space falls within these bounds. However, modern OS
uses more advanced techniques like Paging and Virtual memory which will be talked about later.

Address Binding
---------------

Usually you have programs that reside in secondary memory, waiting to be brought into main memory once a CPU becomes available.

A program can live anywhere in physical memory, because of the advent of Virtual memory and paging. 
This meaning a new program need not be at x00000, but can be anywhere in the physical address.


Address binding is the process of addresses in physical memory being binded to your programs symbolic addresses that are actually
just hanging, but once the binding happens, those symbolic addresses get mapped to main memory addresses.

Now the binding happens through a process called relocatable code, which just means that code doesn't get main memory addresses
until loading time. So when it becomes an object file and right before it becomes a binary file, the compiler gets a note that tells
it when you get the time during the loading phase, please assign it a main memory address

Address binding can happen at 3 seperate places. At compile time, basically when the code becomes an Assembly file (.s), 
during Load time when the file becomes a (.o) file, or during execution time when the file goes from becoming a (.exe) to a (.so)
Basically, execution time binding happens as the program is running routine by routine, right before it gets to a routine, the routine gets 
assigned a main memory address.

**********
IMPORTANT:
**********
 Preprocessing (things like #include) -> .i file -> Compilation -> Assembly file .s -> Assembler -> Turns assembly into 
object files (.o) -> Linker -> links multiple object files and libraries (.exe for windows or .so for Linux)


Unlike compile time where an absolute address is loaded or during load time where a base address (only known at load time) + 
relative address is loaded, execution time loads the virtual address given to it.

Logical address also called virtual address is generated by the CPU and is attached to a physical address with the same size,
but not always the same location for execution time, which is our focus since that's what all the most modern and popular OS's use.

The Memory Management Unit (MMU) does the mapping in real time.

Modern OS systems don't use relocation register but rather use Page tables

Dynamic loading
---------------

This type of loading happens where parts of the code are only loaded into Main memory when the specific routine is run/called

DLL - Dynamically Linked Libraries are libraries that can be accessed by multiple programs at once and are only linked during
execution time. The entire library (aka file) gets loaded into virtual memory (carved out space, not actually mapped to physical addresses), 
and then the main program that called the library function gets linked to that main program address at the same time that the library
function gets mapped to a physical address space (this is called Lazy Linking).

Bruh soo much confusion I typed above. Basically the main memory routine gets mapped to a physical address, but if that routine
calls a function from the library, that library function gets linked to that physical address at the same time the library function
also gets mapped in main memory.

  a physical address. That happens lazly when that specific routine in the library is called.


Contiguous memory allocation
----------------------------

Memory must support both OS and User processes, therefore it must partition memory between these two processes.
Usually its high memory reserved for kernal space while lower memory is reserved for user space.

Each process is contained in its own Contiguous portion of memory, this doesn't mean that there isn't fragmentation or anything like that.

Some embedded systems still use relocation registers (base register + limit register) not for memory mapping but to 
ensure security and not accessing memory they don't have permission for. The MMU is passive, it gets told what to do and it checks certain 
registers. The Kernal is what does all the register allocation and controlling the memory mapping business.


Memory Allocation - Variable Partition
--------------------------------------

You can do partitioning of memory to ensure that each process gets its own partition of memory that is big enough to support it.

Variable-partitioning has preallocated sizes for efficiency

Holes are assigned processes that are big enough to support it.

When a process exists (meaning its either done or doesn't require memory) it frees a parition which combines with the holes around it

Very important: Multiprogramming is limited by the # of partitions

Dynamic Storage ALLOCATION
--------------------------

How do you allocate a process with size n into the existing holes?

1. First-fit: You find the first big enough hole.
2. Best-fit: Allocate the smallest-hole in the list that is big enough to support the process.
3. Worst-fit: Allocate the largest hole; must also search the whole list
  - Number 3 plays into best-fit, because it leaves smaller holes that can be fit for smaller processes

Simulations show that in terms of speed and storage utilization, first-fit and best-fit are the best.
Neither is the winner, but first-fit is faster.

Fragmentation
-------------

You have two types of ways main memory gets fragmented:

1. External Fragmentation: When you allocate varaible sized blocks based on different sized processes anywhere in the main memory.
2. internal Fragmentation: When you have pre-defined contiguous fragmentation, but a process may not occupy all of it, however that
fragment can't be used even if some space is left unoccupied.

External fragmentation is no longer used, because when a process is loaded then freed, it can cause small fragments everywhere 
that can't be used by bigger processes, even though those processes can fit in terms of total fragments available. 

When using First-Fit statistical analysis (External): We note that given N allocated blocks, 0.5N blocks will be lost to fragmentation
This means overall 1/3 of memory will always remain unusable.
So if you have 100 Fragments allocated, 50 will be lost to fragmentation. This means 50/150 will be lost due external fragmentation.

One way to REDUCE external fragmentation is through compaction, which is basically shuffling all free memory into one location.
This is ONLY POSSIBLE if you do dynamic reallocation during execution time. But this is very very expensive. 

Fragmentation is always a problem in memory allocation, but a few solutions alongside compaction exist, such as:

1. Backing store: Where we copy a process out to secondary memory, then we bring it back later into a more contiguous memory location,
or freeing up conitguous memory blocks for more higher priority processes. This causes a lot of I/O overhead. 
2. Paging: Allows the physical address space but not the logical address space to be noncontiguous. (Ultimate fix for now)

PAGING 
------

Paging basically allows the physical address to be noncontiguous.

Once physical space is available, a process gets assigned to that physical address space
- This avoids external fragementation (aka noncontiguous blocks of memory wasting 1/3 of memory addressing space)
- Avoids the problem of varying memory chucks

With paging you first divide the physical memory in power of 2 chunks (because of binary) called Frames
You then divide the same sized memory in logical spaces called Pages

To run a program of N pages, you need N frames

Setup a PAGE TABLE to translate logical addresses to physical addresses

You still have internal fragmentation which is better than external fragmentation which renders 1/3 of memory useless

Backing store is also split into pages

Address Translation Scheme
--------------------------

The address generated by the CPU is divided into two parts:

1. Page number (p), which allows indexing into the page table, which gives you the base address in memory
2. Page offset (d), this is the offset applied to the base address

p = m - N

d = n

- m represents the bits that represent the logical address size, so on 64 bit systtms, they usually wire up 48 bits for addressing,
which gives you 2^48 logical address spaces.
- n represents the bits that represent the page offset

***IMPORTANT***: How the math done is so...
When the CPU generates a logical address of size 2^M and the page table that's a part of this architecture is 2^N,
then higher order m - n bits is the page number while the lower n bits are the page offset.

Example: Let's say you have a logical address space of 16MB and a page size of 8KB (8KB in binary translates to 8192)...
How many bits are required to represent the page offset? it would be log2(8192) = 13 bits
How many bits required to represent the logical addres log2(16777216) = 24 bits
How many bits is the page number = 11 bits

Another example: Given a page size of 1KB, what is the page number and offset of the following decimal address 650000
1KB translates to 1024. So page # is: 650000/1024 = 634.7, because mod takes that .7 it's 634.
Page offset is 650000mode1024 = 784

Doing log2 of page size tells you how many bits the offset needs (aka the size of the offset).
One hexadecimal value represents a nibble aka 4 bits. 1 byte is 8 bits, so two hexadecimal values represent a byte.

Paging Model of Logical and Physical Memory
-------------------------------------------

The MMU translates a logical address generated by the CPU into a physical address, here's how it's done:

1. Extract the page number p and use it to index into the page table.
2. Then extract the frame number f from the page table.
3. Replace the page number p with the frame number f.

As the offset d doesn't change because we know how big a frame size is, we don't replace it.
The replaced page number + the offset give us the physical address.

**UNDERSTANDING**: A process is a whole executable file that's given a page or multiple pages. Now page number gives you 
the start of the execution file, and offset gives you the exact byte to execute. Paging is what allows ADDRESS BINDING 
and DYNAMIC LOADING to happen. Paging allows logical address to get bounded to physical address.

m tells you the # of bits that represent the logical address space, so 4 bits give you 16 different address
n tells you the page and the offset size in bytes by doing 2^n, so n = 2 doing 2^2 gives you 4 bytes.
So know we frames is 4 bytes. So if physical memory is 32 bytes, then 32/4 gives you 8 frames.

On Average, you get an internal fragementation of about 1/2 frame size per process.

Page sizes
----------

A page table is usually made for 4KB sized pages, and in a 32-bit system the physical address space is 4 bytes, meaning the table entries
can be 4 bytes, which means one table can have 1024 entries. 

This would mean in a 32-bit system, the page size would be 2^32, that's how big the logical address is. So taking 2^32 and dividing 
it by 4KB you get the maximum page tables you would need. 

Also, that means if you have 8GB ram, you would have 8GB / 4KB fragments and that's the total number of fragments.

Everytime a process is mapped virtual memory, that virtual memory is given a stack and a heap, now the bigger the programs, the more far
a part the stack and the heap are, the memory in between now becomes unused and creating page tables for all of that unsused memory in 
between becomes too much, so we create multi layer tables that point only to parts of the lower table that are used.

However, this causes problems for TLB misses, because lets say a programs virtual to physical memory translation isn't in the cache,
that's a TLB miss, so you must now do table walkthrough, now this walkthrough is very expensive in terms of time, therefore to avoid this
headache, we have certain fragments that can be 2MB, 4MB or even 1GB, and we simply allocate these large programs to that fragment.
Note now, that for a 1GB page, the offset becomes larger, which inherently means the tables become larger so the depth to do table travel
isn't that much because less tables can now contain more conitguous addresses.
